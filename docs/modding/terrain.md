# Terrain models and heights

> AI-generated, local to this fork. Do not upstream.

How to replace or make a cell's 3D terrain and the heights the player walks on.
A cell is one 32 × 32-tile square of a map, `data/landdata/NNNN/`
([maps-and-warps.md](maps-and-warps.md#terrain-datalanddata)). Its terrain is
two files:

| File | What it is | Edit with |
|---|---|---|
| `model.nsbmd` | the 3D model you see (NITRO-System NSBMD) | `mapkit terrain export` → Blender (or any OBJ editor) → `mapkit terrain import` |
| `terrain.bdhc` or `heights.json` | the heights you walk on (BDHC) | generated by `terrain import`, or `heights.json` by hand, or `mapkit heights ...` |

Collision and tile behaviors stay in `permissions.txt` (the map editor paints
them). The game doesn't derive one from the other, so when the ground changes
shape, update all three.

## Quick start

```sh
tools/mapkit/mapkit.sh terrain export 4 work/cherrygrove     # cell 4 is Cherrygrove
# edit work/cherrygrove/model.obj in Blender, export it back as OBJ (same folder)
tools/mapkit/mapkit.sh terrain import 4 work/cherrygrove/model.obj --dry-run   # check first
tools/mapkit/mapkit.sh terrain import 4 work/cherrygrove/model.obj
tools/mapkit/mapkit.sh terrain check 4
make release
```

Which cell a map uses: `layout.json` of the map's layout lists them (the map
editor's status bar shows the cell under the cursor).

## What export writes

```
work/cherrygrove/
  model.obj        the terrain (object "terrain") and its heights (object "heights")
  model.mtl        one material per model material, with its texture
  textures/*.png   the textures, decoded from the area's texture archive
  terrain.json     what OBJ can't hold: per material texture, palette and drawing settings
```

- Units: one OBJ unit is one model unit; a tile is 16. `--scale 16` makes one OBJ
  unit one tile (import reads the scale back from `terrain.json`).
- Axes: x east, y up, z south, origin at the cell's centre. The cell spans −256 to
  256 in x and z. These are OBJ's usual y-up axes; in Blender, import and export
  with "Y up, −Z forward" (the defaults).
- Lit materials export normals (`vn`); unlit ones export vertex colors as
  `v x y z r g b` (Blender keeps them as a color attribute).
- Textures are the area's, so the export depends on which area shows the cell;
  give `--area N` when a cell is used by maps of different areas.

## Making the model

Rules the game imposes:

- **Textures come from the area.** A cell has no textures of its own: when the map
  loads, the game binds each material to the texture and palette **of the same
  name** in the area's map texture archive (`map.json` `area_data` → area header
  `files/a/0/4/2` → `files/a/0/4/4`). You can use any texture in that archive;
  adding new textures isn't supported yet.
- **Size.** The whole `model.nsbmd` must fit in 0xF000 bytes (61,440; the game's
  map model buffer). Every retail model fits; `import` reports the size and
  refuses a model that doesn't. A flat cell of 1,024 quads uses about 0xA400.
- **Polygons** are triangles or quads. Convex quads stay quads (cheaper); concave
  ones and n-gons are split into triangles. Texture coordinates are stored as
  ±2048 texels per polygon; repeating textures are shifted back into range.
- **One model, one node.** Everything is in model space; object transforms in
  Blender are applied by its OBJ exporter.

### Materials

`terrain.json` keeps, per material name:

```json
"grass01": {
    "texture": "grass01gs", "palette": "grass01",
    "lit": true, "alpha": 31, "cull": "back", "fog": true,
    "repeat": [true, true], "flip": [false, false],
    "diffuse": [25, 25, 25], "ambient": [31, 31, 31]
}
```

| Key | Meaning |
|---|---|
| `texture`, `palette` | names in the area's texture archive (`null`: untextured) |
| `lit` | lit by the area's lights using normals; `false`: vertex colors only (pre-lit, like most of the retail models' cliffs and roads) |
| `alpha` | 0-31 (31 opaque) |
| `cull` | which faces are hidden: `back` (default), `front`, `none` |
| `fog` | takes the map's fog |
| `repeat`, `flip` | texture wraps (and mirrors) along s, t |
| `diffuse`, `ambient` | material colors, 0-31 per channel |

A material that isn't in `terrain.json` is worked out from the MTL:
- the texture from its `map_Kd` file name (`textures/<texture>-<palette>.png`, or
  `<texture>.png` with the palette `<texture>_pl` or `<texture>`);
- the alpha from `d`;
- `lit` if its faces have normals, else unlit with the vertex colors (white if
  none).

So to use another texture of the area in Blender, assign one of the exported
PNGs, or copy and rename one; add an entry to `terrain.json` for anything else.

## Heights

The game finds the player's (and every NPC's) height from the cell's BDHC: a list
of **plates**, rectangles along x and z, each with a plane that gives the height
inside it. Where plates overlap (a bridge over a path), the game takes the height
nearest to where the walker already is. Outside every plate there is no height
and the walker keeps the one it had.

`terrain import` makes the heights in one of three ways:

1. **From an object named `heights`** (or `collision...`) in the OBJ, if there is
   one. Every face of it that is a rectangle along x and z becomes exactly one
   plate (flat or sloped). Other faces are sampled like the model (2).
   Export writes the cell's current heights as this object, so editing those
   rectangles in Blender edits the heights exactly.
2. **Otherwise from the model**: every face pointing up (normal y ≥ 0.5) is
   sampled on an 8-unit grid (`--grid`) and the grid cells merged into plates.
   The result follows the model's own surface: on retail models it matches the
   model at 99.99% of tile centres. `--walkable-only` restricts it to tiles that
   `permissions.txt` doesn't mark as collision (keeps roofs and backdrops out).
3. `--heights keep` leaves the heights alone.

Generated heights are written to `heights.json` (and `terrain.bdhc` is removed);
the build compiles it.

The retail heights were made from separate collision data, not from the visible
model: interiors often stand 2-3 units above the drawn floor, and invisible floors
exist. Generating from a retail model gives the model's surface, not the original
heights; use a `heights` object (or keep them) where that matters.

### heights.json

```json
{
    "plates": [
        {"x": [-256, 0], "z": [-256, 256], "y": 0},
        {"x": [0, 128], "z": [-128, 0], "y": 32},
        {"x": [-64, 0], "z": [-128, -96], "ramp": {"along": "x", "y": [0, 32]}},
        {"x": [64, 96], "z": [0, 32], "normal": [0, 0.70703125, 0.70703125], "d": -45.25}
    ]
}
```

- `x`, `z`: the rectangle, `[min, max]` in model units from the cell's centre.
- A height is one of: `y` (flat); `ramp` (rising linearly along `x` or `z` from
  `y[0]` at the low edge to `y[1]` at the high edge); `normal` + `d` (the plane
  `normal · (x, y, z) + d = 0` as the file stores it).
- Numbers are multiples of 1/4096.
- Plates may overlap (bridges, upper floors). Keep fewer than 10 over any one point:
  the game ignores the rest.

```sh
tools/mapkit/mapkit.sh heights decompile 4      # terrain.bdhc -> heights.json (same heights)
tools/mapkit/mapkit.sh heights show 4           # list the plates
tools/mapkit/mapkit.sh heights at 4 16 12       # the height the game finds at tile (16, 12) of the cell
tools/mapkit/mapkit.sh heights generate 4       # replace them with heights from model.nsbmd
tools/mapkit/mapkit.sh heights compile 4        # heights.json -> terrain.bdhc
```

`decompile` keeps every height; for 52 retail cells the compiled file orders its
internal tables differently (so the ROM differs), and `decompile` says so.

## Checking

`mapkit terrain check [cells]` reports what the game would trip on:

- a model over 0xF000 bytes, or not exactly one model;
- a material whose texture or palette isn't in the area of a map that shows the cell;
- both or neither of `terrain.bdhc` and `heights.json`;
- heights over the game's 0x9000-byte buffer, a vertical plate (no height), more
  than 10 plates over a point.

`mapkit format check` also validates `heights.json`.

The unmodified game already gives 19 findings, so compare against those: land data
212 and 432 are shown only by unused maps (`Saffron_Unused`, `SeafoamIslandsUnused`)
whose areas lack their textures; a `bike_02_2` material (cells 241, 280, 281, 359,
372) and two others (333, 566) name textures their interiors' areas don't have;
cell 464 has the vertical plate.

## What has been verified

- All 676 retail models read and write back byte for byte, and their geometry
  re-encodes through `build_terrain` unchanged (smaller than the originals on
  average). All 676 BDHC files read and write back byte for byte, and the heights
  of `heights.json` equal the originals at every point tested.
- Export then import gives the same model and heights (tests).
- The build packs `heights.json` and new models, and notices new or removed files
  without reconfiguring.
- **Not verified in the game**: no emulator was available. The files are built the
  way the retail ones are (same structure, same conventions), but load a modified
  cell in an emulator before building on it.

## Not supported yet

- New textures (adding them to an area's texture archive), and texture
  animations (water, flowers).
- Prop placement in the editor (edit `props.json`).
- The meaning of a cell's `altitudes` for heights: the game draws a raised cell's
  model higher but uses its BDHC heights unchanged, and how the two agree on
  raised walkable cells isn't worked out. Keep new walkable terrain in cells with
  altitude 0, or check in game.
